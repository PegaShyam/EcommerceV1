## 1. What this commit does

This is the **scaffolding commit**. No business logic yet — it just lays down two independent projects and their tooling:

- `backend/` — a Node.js + TypeScript + Express API server.
- `frontend/` — a React app, built and served by Vite.

Think of it as pouring the foundation before building any rooms. Everything here is either generated by a CLI tool (`npm create vite@latest`, a manual `npm init`) or hand-written config that tells the tools how to behave.

## 2. Why two folders — `backend` and `frontend`

This project keeps the **server** (backend) and the **browser app** (frontend) as two separate Node projects in one repository:

- Each has its own `package.json`, so each has its own independent dependency list and its own `npm run <script>` commands.
- They can be developed, tested, and deployed independently (e.g. the frontend could be deployed to a static host, the backend to a Node server).
- Neither needs the other's dependencies installed — the backend doesn't need React, the frontend doesn't need Express.

This pattern is sometimes called a "monorepo" (informally) even without a dedicated monorepo tool (like Turborepo or Nx) tying them together — here, they're just two sibling folders.

## 3. Root `.gitignore`

```
node_modules
dist
dist-ssr
*.local
.env
```

A few lines worth calling out:

- `node_modules` — never commit installed packages. They're regenerated from `package.json`/`package-lock.json` by anyone who clones the repo and runs `npm install`. Committing them would bloat the repo with megabytes of code that isn't even yours.
- `dist` / `dist-ssr` — build output folders. These are *generated*, not *authored* — if you can regenerate a file with a build command, it doesn't belong in git.
- `.env` — **this is a security rule, not a tidiness rule.** `.env` files hold secrets (API keys, database passwords). If this line weren't here, a future `git add .` could leak a secret into git history — and once something is in git history, deleting the file later does *not* remove it from past commits.

**Best practice:** `.gitignore` is written *before* you generate the tools that create ignorable files (which is exactly the order this commit follows — `.gitignore` is the first file in the diff).

## 4. Backend setup

### 4.1 `backend/package.json`

```json
{
  "scripts": {
    "dev": "tsx watch ./src/index.ts",
    "build": "tsc",
    "start": "node ./dist/index.js"
  },
  "type": "commonjs",
  "dependencies": { "express": "^5.2.1", "cors": "^2.8.5", "dotenv": "^16.4.7", ... },
  "devDependencies": { "typescript": "^5.7.3", "tsx": "^4.19.2", ... }
}
```

Key terms:

- **`scripts`** — shortcuts run via `npm run dev`, `npm run build`, etc. Three different scripts exist for three different situations:
  - `dev` — for local development. `tsx watch` runs TypeScript *directly* (no separate compile step) and restarts the server automatically whenever a file changes. Fast to iterate with.
  - `build` — compiles TypeScript (`.ts`) down to plain JavaScript (`.js`) in `dist/`, using the real TypeScript compiler (`tsc`). This is what you'd run before deploying.
  - `start` — runs the *compiled* output with plain Node.js. This is what production actually runs — no TypeScript tooling needed at runtime, just Node.
  - The reason there are two different ways to run the app (`dev` vs `build`+`start`) is that development favors speed of iteration, while production favors a minimal, predictable runtime.
- **`"type": "commonjs"`** — tells Node which module system this package uses: `require()`/`module.exports` (CommonJS) rather than `import`/`export` (ES Modules) at the *compiled* JS level. TypeScript still lets you *write* `import` syntax either way; this field controls what the compiled output looks like and how Node loads it.
- **Notice dependencies already installed that aren't used yet**: `@clerk/express`, `stream-chat`, `@imagekit/nodejs`, `standardwebhooks`, `zod`, `drizzle-orm`, `pg`. None of these are imported anywhere in this commit. This tells you the dependency list was planned ahead of time — a good sign the author already had an architecture in mind (auth via Clerk, chat via Stream, images via ImageKit, webhooks, a Postgres database via Drizzle). Seeing "installed but unused" dependencies in a diff isn't a mistake — it's often a preview of upcoming commits.

### 4.2 `backend/tsconfig.json`

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "outDir": "dist",
    "rootDir": "src",
    "strict": true,
    "skipLibCheck": true,
    "esModuleInterop": true,
    "resolveJsonModule": true,
    "declaration": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true
  },
  "include": ["src/**/*.ts"],
  "exclude": ["node_modules", "dist"]
}
```

This file configures the TypeScript compiler. Term by term:

- **`target: "ES2022"`** — which version of JavaScript features TypeScript is allowed to compile *to*. Since this only ever runs on a controlled Node.js server (not an old browser), it's safe to target a recent JS version rather than an older, more-compatible one.
- **`module` / `moduleResolution: "NodeNext"`** — tells TypeScript to follow modern Node.js's own rules for resolving `import` statements (matching how Node.js 12+ actually loads modules), rather than an older/bundler-style resolution.
- **`outDir: "dist"` / `rootDir: "src"`** — compiled output goes to `dist/`, source lives in `src/`. This mirrors the `.gitignore` rule (`dist` is generated, so it's ignored) and the `build`/`start` scripts above (`tsc` writes to `dist`, `node ./dist/index.js` runs it).
- **`strict: true`** — turns on TypeScript's full strictness (no implicit `any`, null-checks enforced, etc.). **Best practice:** turn this on from day one. Retrofitting strict mode onto a large codebase later is far more painful than starting with it.
- **`noUnusedLocals` / `noUnusedParameters`** — the compiler *errors* if you declare a variable or function parameter and never use it. This catches dead code and typos early (e.g. forgetting to actually use an imported function).
- **`skipLibCheck: true`** — don't re-typecheck the `.d.ts` type definitions that come bundled inside `node_modules` packages. This is a pragmatic speed trade-off almost every project makes; the packages' own authors are responsible for their types being correct.

## 5. Frontend setup

### 5.1 `frontend/package.json`

```json
{
  "type": "module",
  "scripts": { "dev": "vite", "build": "vite build", "lint": "eslint .", "preview": "vite preview" },
  "dependencies": { "react": "^19.2.8", "react-dom": "^19.2.8" }
}
```

- **`"type": "module"`** — the opposite choice from the backend. The frontend is allowed to use native ES Modules (`import`/`export`) directly, because it's bundled by Vite for the browser, not run directly by Node. (Different runtime → different module rules is completely normal; don't expect frontend and backend config to match.)
- **`react` vs `react-dom`** — `react` is the library that describes *what* the UI should look like (components, state, JSX). `react-dom` is the renderer that takes React's output and actually paints it into a real browser DOM. They're split into two packages because React can target other renderers too (e.g. React Native for mobile) — `react` stays the same, only the "-dom" part changes per platform.
- **`lint` script** — runs ESLint (a code-quality checker) across the project. Note this is a `devDependency`-only feature: linting isn't needed once the app is built and running, only while writing code.

### 5.2 `frontend/vite.config.js`

```js
import react from '@vitejs/plugin-react'
import { defineConfig } from 'vite'

export default defineConfig({
  plugins: [react()],
})
```

**Vite** is the frontend build tool/dev server. In development, it serves your files instantly using native browser ES modules (no bundling wait); for production (`vite build`) it bundles everything down into optimized static files. The `@vitejs/plugin-react` plugin teaches Vite how to understand JSX syntax and enables **HMR** (Hot Module Replacement — the page updates in-place when you save a file, without a full reload and without losing component state).

### 5.3 `frontend/eslint.config.js`

```js
export default defineConfig([
  globalIgnores(['dist']),
  {
    files: ['**/*.{js,jsx}'],
    extends: [
      js.configs.recommended,
      reactHooks.configs.flat.recommended,
      reactRefresh.configs.vite,
    ],
    languageOptions: { globals: globals.browser, parserOptions: { ecmaFeatures: { jsx: true } } },
  },
])
```

- **`globalIgnores(['dist'])`** — don't lint the build output; it's generated code, not something a human wrote or should fix.
- **`reactHooks.configs.flat.recommended`** — enforces the [Rules of Hooks](https://react.dev/warnings/invalid-hook-call-warning) (e.g. never call `useState`/`useEffect` conditionally or inside loops). Getting this wrong causes some of the most confusing bugs in React, so linting for it automatically is valuable.
- **`reactRefresh.configs.vite`** — makes sure your component file structure stays compatible with Vite's Hot Module Replacement (e.g. a file should mainly export components, not a mix of components and random other exports, or HMR breaks).
- **`globals: globals.browser`** — tells ESLint that identifiers like `window`, `document`, `fetch` are expected globals here (because this code runs in a browser), so it doesn't flag them as undefined variables.

### 5.4 `frontend/src/main.jsx`

```jsx
import { StrictMode } from 'react'
import { createRoot } from 'react-dom/client'
import './index.css'
import App from './App.jsx'

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>,
)
```

This is the entry point — the one place the React app attaches itself to the actual HTML page (`index.html` has a `<div id="root">`).

- **`createRoot(...)`** — React 18+'s API for starting a React tree inside a DOM node (the "concurrent" rendering API, replacing the older `ReactDOM.render`).
- **`<StrictMode>`** — a development-only wrapper that intentionally double-invokes some functions (like component bodies) to help you catch code that isn't "pure" (e.g. side effects run during render). It has **zero effect in production** — it's purely a development safety net.
- **Import order**: CSS import (`./index.css`) comes before the component import (`App.jsx`) — a common convention so global styles are established before component-specific styles/behavior are considered, though in practice CSS import order for bundlers is more about avoiding specificity surprises than strict necessity.

### 5.5 `frontend/src/App.jsx`

This is the default Vite+React template's landing page (hero image, a counter button using `useState`, links to Vite/React docs). Nothing about the actual e-commerce app yet — it exists only to confirm "the app boots and renders" before it's rewritten into the real UI in a later commit.

The one thing worth noting for later: `const [count, setCount] = useState(0)` is the canonical example of **React state** — a value that, when changed via its setter (`setCount`), causes the component to re-render with the new value. This is the same mechanism the real app will use for things like cart contents or logged-in user state.

## 6. Best practices seen in this commit

- **Config before code.** `.gitignore`, `tsconfig.json`, `eslint.config.js`, `vite.config.js` are all committed alongside (or before) the first line of app logic. Tooling decisions made early are cheap; made later, they require retrofitting.
- **`strict: true` from the start** in TypeScript — much easier to keep a codebase strict than to make an existing loose one strict later.
- **Separate `dev` vs `build`/`start` paths** on the backend — optimize for iteration speed locally, and for a minimal, predictable footprint in production.
- **Two independent `package.json`s** rather than one shared one — keeps frontend and backend dependencies from leaking into each other.
